# ADR-0001: basket 的模型与边界

- 状态: Accepted
- 日期: 2026-10-14

**basket** —— 用户创建的一个分享单位，也是一个容器。创建者把本地文件和文件夹（**cherry**）放进篮子（放进去的只是引用，文件本身留在原处），把链接发给别人，拿到链接的人可以挂上它、浏览、取用。

## 前提

这是**两个人之间、有明确沟通的分享场景**。可靠性主要由人来兜底，不是靠软件消除所有失败。这一条前提推翻了大量只有“无人值守的基础设施”才需要的复杂度。

**范围是自用与小范围使用，局域网是主路，不上 Mac App Store。** 不追求规模，不假设用户是陌生人，也不为商店审核做妥协。这一条同样在持续影响决策：不需要为沙盒设计、可以接受“必须两人同时在线”、可以接受“不在同一个网里就用不了”、可以不设计精致的引导流程。

第一条前提有边界条件，否则会被误用：只在错误同时满足「罕见」和「显式」时才成立。于是它落地成两条工程要求：

1. **不允许静默失败。** 每个失败路径都必须有明确、用户能读懂的终态。最坏的情况不是报错，而是展示一份陈旧的列表让人以为文件还在——沟通兜不了这个底，因为没人知道该沟通什么。

   这条的前提是**有人看着**：消息只在有人看的那一刻才有呈现。所以要求不是「每个失败都得弹给人看」——半夜被删掉的源文件，谁也不在看——而是「有人看的时候不许说假的」，加上「错过的那些至少留在日志里」。
2. **可恢复优先于可理解。** 沟通能解释错误，但不能退还已经花掉的半小时和流量。这一条原来落地成“断点续传是必要条件”，**现在我们不提供它**：传输是内核的 NFS，一次拷贝中途断了就得重来（要续传就用 `rsync` 这类标准工具）。这是走 NFS 换来“对方零安装”的代价之一，记在 ADR-0007。

具体的失败清单见 `docs/errors.md`。

## 背景

关键约束：**创建者是 basket 里所有内容的唯一源**。创建者不在线，这个 basket 就不可用。

由此推出本决策的基础：一个 basket 只有一个写者，不存在共享可变状态，也不存在需要收敛的并发写。

这也是"多人往同一个 basket 里共享文件"方案被放弃的原因：既然内容只能由各自的机器提供，"多人共用一个 basket"和"每人各建一个 basket"在能力上等价，前者只凭空引入成员表、入口发现和权限模型。

## 决策

**一、basket 是一篮 cherry，不是一个目录。** 文件本身永远留在原处，basket 里只记录引用。一颗 cherry 是 `名字 + 源路径 + 类型（文件 / 文件夹）`：

- 名字由用户给定（默认取原文件名），在 basket 内必须唯一。
- cherry 的名字是 listing 里的顶层名字，cherry 内部的相对路径挂在它下面。单文件的 cherry 在 listing 里就是它自己的名字。所以不存在“basket 的根”这个概念，每颗 cherry 自带根。
- 重命名 cherry 只改显示路径，不动磁盘上的文件。用户可以自由地在 basket 里重新组织。
- **不做内部检查**：不检查源路径的重复，也不检测一颗 cherry 是否位于另一颗之下。cherry 的列表就是一张列表。后果是 listing 里可能出现指向同一文件的多个路径——这是创建者自己的选择，代价只是对方那边看起来多一份。

**二、共享语义是引用（live index），不是快照。** basket 里的 cherry 指向创建者磁盘上某个路径的当前状态：路径还在就跟着它走，文件被改了对方下次读到的就是新的内容，被删除或移走那就读不到了。**对方拿到的不是"一份推送过来的副本"**：字节是从创建者磁盘上现读的，创建者改了什么，对方下一次读就看到什么。

引用失效时**服务发现就把它摘掉**，只留一条日志：篮子里不留死的引用，一条打不开的名字留着没有意义，还会让整个篮子根列不出来。发现的机会是三个把篮子内容报出去的地方——列篮子根、`cherry show`、`cherry list`。

**「失效」只认确定不存在**（`ENOENT`，或那里已经不是文件也不是真目录了）。权限、IO、外置盘掉线之类的错可能是一时的，摘掉就再也回不来，所以那些留着不动，只记日志。

**三、不引入分布式状态。** 不用 `iroh-docs`，不用 gossip，不用 CRDT，不用成员表。basket 的目录由创建者现算，形态见 ADR-0002。

**四、传输就是创建者侧的一个只读 NFS 导出。** 对方用系统自带的客户端挂，我们不写客户端。完整的理由、权限模型，以及只读、不共享符号链接这两条边界，见 ADR-0007。

iroh 整套暂时删掉；将来真的需要跨网时，加回来的是**一个端口转发**，不是一套新的数据协议。

## 非目标

以下都是产品形态的直接推论，写在这里是为了防止将来被当成"免费优化"重新引入：

- **不做跨 basket 的内容去重**。两个 basket 里放了字节相同的文件，就是两份互不相干的记录。路径是主键。
- **不做多源下载**。每个文件只有一个源，就是创建者的那台机器。
  （这条约束的是**源的数量**，不是连接或流的数量：对同一个源开多条连接、分别取不同字节区间，不违反这一条。那只是把一条流水线拆成几条，源还是那一个，也不涉及任何跨源的调度或校验。）
- **不做自动做种 / 常驻缓存节点**。"我的下载就是我的下载"，下载下来的副本不会自动成为别人可用的源。要再分享就再建一个 basket，即使字节完全相同。
- **不做本地资产库，也不做服务端缓存。** 创建者读的就是用户文件系统里那个文件本身，中间没有副本；对方那边的缓存归内核的 NFS 客户端管。所以没有 store、没有淘汰策略、没有 pin / GC 生命周期这些事情。
- **不做可用性广播**。"谁手里有这份内容" 不在本产品范围内。
- **不做成员表**。basket 没有"成员"，只有创建者和查看者。

## 后果

正面：

- **协议面为零**：我们不定义任何线上协议（NFS 是内核的事），只定义一条链接的文本格式。没有 CRDT、gossip、store、redb。
- “取消分享”语义平凡：从 basket 里移除一颗 cherry 就是移除，没有需要清理的远端状态。

负面：

- **只有同一个局域网能用。** 跨网要等 ADR-0007 决策六里的那个端口转发。
- **`basket_id` 在局域网里是明文传的**（NFSv3 不加密），而且会留在对方的挂载表和 shell history 里。这是能力式链接的通病。
- 创建者离线 = 这个 basket 不可用。这是产品定位，不是缺陷。
- 列出目录的开销随 cherry 数量线性增长。第一版不优化。

## 备选方案

1. **`iroh-docs` 作为账本** —— 弃。它是为多写者收敛设计的，本产品没有这个问题，却要付出三协议栈与版本滞后的代价。
2. **多人共享进同一个 basket + gossip 成员发现** —— 弃。见背景。
3. **中心化目录服务** —— 弃，与产品前提冲突。

## 重新评估的触发条件

- 出现**常驻服务器上的 basket**需求（大家往一台固定机器上传、取用）。这不推翻本 ADR：届时唯一的变化是创建者从一台个人机器变成一台固定地址的机器。
- 出现**自动做种 / 常驻缓存节点**需求，即某人下载后的副本要成为创建者离线时的可用源。这是唯一能推翻"单写者 + 单源"前提的需求。

## 附注

共享边界（`..` 和符号链接都不许穿过）见 ADR-0007 决策四。链接的文本格式与协议面见 ADR-0002。
