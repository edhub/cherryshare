# ADR-0001: tap 的模型与边界

- 状态: Proposed
- 日期: 2026-10-14

**tap** —— 用户创建的一个分享单位，里面可以放任意数量的文件和文件夹。创建者把链接发给别人，拿到链接的人可以浏览、下载。

## 前提

这是**两个人之间、有明确沟通的分享场景**。可靠性主要由人来兜底，不是靠软件消除所有失败。这一条前提推翻了大量只有“无人值守的基础设施”才需要的复杂度。

它有边界条件，否则会被误用：只在错误同时满足「罕见」和「显式」时才成立。于是它落地成两条工程要求：

1. **不允许静默失败。** 每个失败路径都必须有明确、用户能读懂的终态。最坏的情况不是报错，而是展示一份陈旧的列表让人以为文件还在——沟通兜不了这个底，因为没人知道该沟通什么。
2. **可恢复优先于可理解。** 沟通能解释错误，但不能退还 4 GB 的流量和半小时。所以断点续传是这条原则的必要条件，不是优化。

具体的失败清单见 `docs/errors.md`。

## 背景

关键约束：**创建者是 tap 里所有内容的唯一源**。创建者不在线，这个 tap 就不可用。

由此推出本决策的基础：一个 tap 只有一个写者，不存在共享可变状态，也不存在需要收敛的并发写。

这也是"多人往同一个 tap 里共享文件"方案被放弃的原因：既然内容只能由各自的机器提供，"多人共用一个 tap"和"每人各建一个 tap"在能力上等价，前者只凭空引入成员表、入口发现和权限模型。

## 决策

**一、tap 是一个条目列表，不是一个目录。** 文件本身永远留在原处，tap 里只记录引用。一个条目是 `名字 + 源路径 + 类型（文件 / 文件夹）`：

- 名字由用户给定（默认取原文件名），在 tap 内必须唯一。
- 条目名是 listing 里的顶层名字，条目内部的相对路径挂在它下面。单个文件条目在 listing 里就是它自己的名字。所以不存在“tap 的根”这个概念，每个条目自带根。
- 重命名条目只改显示路径，不动磁盘上的文件。用户可以自由地在 tap 里重新组织。
- **不做内部检查**：不检查源路径的重复，也不检测一个条目是否位于另一个条目之下。条目表就是一张列表。后果是 listing 里可能出现指向同一文件的多个路径——这是创建者自己的选择，而且因为内容寻址，不会造成重复传输。

**二、共享语义是引用（live index），不是快照。** tap 里的条目指向创建者磁盘上某个路径的当前状态：路径还在就跟着它走，文件被修改则重新索引，被删除或移走则从列表里移除。接收方下载到的是一次性副本，创建者后续的修改不会推送过去。

**三、不引入分布式状态。** 不用 `iroh-docs`，不用 gossip，不用 CRDT，不用成员表。tap 的目录由创建者现算，形态见 ADR-0002。

**四、iroh 的职责收窄为三件事**：NAT 穿透、加密、身份。不需要公网 IP、证书、DNS 或服务器。

## 非目标

以下都是产品形态的直接推论，写在这里是为了防止将来被当成"免费优化"重新引入：

- **不做跨 tap 的内容去重**。两个 tap 里放了字节相同的文件，就是两份互不相干的记录。路径是主键，内容 hash 只是传输标识。
- **不做多源 / 并行下载**。每个文件只有一个源，就是创建者的那台机器。
- **不做自动做种 / 常驻缓存节点**。"我的下载就是我的下载"，下载下来的副本不会自动成为别人可用的源。要再分享就再建一个 tap，即使字节完全相同。
- **不做本地资产库**。iroh-blobs 的 store 只是传输工作区，不为它维护 pin / GC 生命周期；持久的那一份永远是用户文件系统里的普通文件，下载导出到用户目录后即可回收。
- **不做可用性广播**。"谁手里有这个 hash" 不在本产品范围内。
- **不做成员表**。tap 没有"成员"，只有创建者和查看者。

## 后果

正面：

- 协议面极小：只有 iroh-blobs 加一个自研 ALPN。没有 CRDT、gossip、redb。
- 无第三方 0.x crate 的版本滞后风险。
- "取消分享"语义平凡：新目录里没有这一项就是删了。

负面：

- 创建者离线 = 这个 tap 不可用。这是产品定位，不是缺陷。
- 列出目录的开销随条目数线性增长。第一版不优化。

## 备选方案

1. **`iroh-docs` 作为账本** —— 弃。它是为多写者收敛设计的，本产品没有这个问题，却要付出三协议栈与版本滞后的代价。
2. **多人共享进同一个 tap + gossip 成员发现** —— 弃。见背景。
3. **中心化目录服务** —— 弃，与产品前提冲突。

## 重新评估的触发条件

- 出现**常驻服务器 tap**需求（大家往一台固定机器上传、取用）。这不推翻本 ADR：届时唯一的变化是创建者从一个 EndpointId 变成一台固定地址的机器。
- 出现**自动做种 / 常驻缓存节点**需求，即某人下载后的副本要成为创建者离线时的可用源。这是唯一能推翻"单写者 + 单源"前提的需求。

## 附注

创建者地址的解析依赖 iroh 自带的 DNS / pkarr 发现，NAT 穿透由 iroh 负责。这两件事仍然要自己接，但不需要自己实现。

创建者侧能否避免把文件复制进 store，取决于 iroh-blobs 的引用模式（`ExportMode::TryReference` 只是 hint，不保证）。这是实现问题，不影响本决策：即便需要临时复制，store 也不是资产库。
