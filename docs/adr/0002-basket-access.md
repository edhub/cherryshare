# ADR-0002: basket 的访问方式

- 状态: Accepted
- 日期: 2026-10-14

## 背景

访问一个 basket 要回答两件事：源在哪，以及看的是哪个 basket。ADR-0001 已经定了 basket 只有一个源、内容只能从它取。这里定链接形态和两者之间的协议。

## 决策

### 链接

分享的单位就是一个 link：

```rust
struct BasketLink {
    addr: EndpointAddr,    // endpoint id + relay url + 直连地址
    basket_id: [u8; 16],   // 128-bit 随机（CSPRNG）
}
```

- `basket_id` 是凭证，不是索引：谁拿到谁就能看。吊销 = 换一个新 `basket_id`。
- 一个 endpoint 可以持有任意多个 basket，各自独立的 `basket_id`。
- 编解码走 `iroh-tickets` 的 `Ticket` trait（`KIND = "cherryshare"`，postcard 序列化 + 首字节版本号），不自己发明字符串格式。
- 带完整的 `EndpointAddr` 而不是只带 `EndpointId`，理由见下面的依赖面。

### 协议

自研 ALPN，两个请求：

- `GetListing(basket_id)` → 创建者现算并返回目录 `[(路径, size, mtime)]`。
- `GetFile(basket_id, 路径)` → 返回 `{hash, size}`。之后查看者按 hash 走 iroh-blobs 的原生 ALPN 取字节，不自己传文件。

**目录里没有 hash，这是故意的。** 昂贵的工作被拆成两层，各自在合适的时机发生：

- `GetListing` 只做廉价的部分——遍历 + stat，产出 `路径 → (size, mtime)`。耗时只与 cherry 数量有关，与“内容变了多少”无关。所以打开一个 basket 总是很快，哪怕创建者刚改了几十 GB。
- `GetFile` 才做昂贵的部分——拿 `size + mtime` 与持久化的索引缓存比对，没变就命中缓存，变了才读文件算 hash。

由此还省掉一件事：创建者改了一个大文件但没人下载它，就永远不用为它算 hash。

推论：查看者点下载之后会有一段等待（创建者读文件算 hash，必要时还要导入 store）。这段等待**只与被点的那一个文件的大小成正比，与 basket 里有多少文件无关**，而且必须有明确的状态和进度（“创建者正在准备文件…”），否则就是“点了没反应”。

**没有文件监听器。** 没有人看的时候，索引新不新没有意义，所以触发点就是请求本身。扫描异步进行、按 cherry 容错（单个文件读不到只影响那一颗）。持久化的索引缓存（`路径 → size/mtime/hash`）是必需的：没有它，比对这一步就退化成“读一遍所有内容”。

### 目录是响应，不是制品

没有签名的清单 blob，没有版本号，没有本地缓存。

- **不需要签名**：连接本身已经认证到创建者的公钥，响应就是从创建者那儿来的。签名只在目录要经第三方转手时才有意义，而那正是非目标里不做的事。
- **不需要版本号**：打开时现取就是最新的。浏览期间创建者要提示"变了"，一个空消息就够。
- **不需要本地缓存**：创建者离线时 basket 本来就不可用，展示一份陈旧目录只会误导。

### 依赖面

默认配置依赖两样公共基础设施：地址解析走 n0 的 DNS / pkarr，连接打不通时兜底走 n0 的公共 relay。n0 自己说公共 relay 适合开发测试、不建议用于生产——但本产品的范围是自用小范围，所以这不构成阻碍。

另外显式开启**本地发现**（mDNS，`discovery-local-network` feature，默认关闭）：它让同一局域网内的解析更快，也让完全没有公网时仍能工作。既然局域网优先，默认开。

iroh 还提供两条退出通道，现在不做，但要知道它们存在：自建 relay（`RelayMode::Custom`）；纯局域网零外部依赖（`RelayMode::Disabled` 加本地发现）。

`BasketLink` 带完整的 `EndpointAddr` 而不是只带 `EndpointId`，所以在上面任何一种配置下都能用：LAN 模式下多带的地址信息只是冗余，而组播被网络设备挡住时它还能兜底。

## 非目标

- **不用短 id**（32-bit 一类的本地不重复 hash）。
- **不做 token 兑换层**（用外层 token 换真正的 `basket_id`）。
- **不做次数预算**（"这个链接最多被兑换 1000 次"）。
- **限流不作为访问控制**。

## 理由

**为什么 `basket_id` 是 128 bit。** 短 id 满足的是唯一性，这里真正需要的属性是不可猜测性。而要枚举，前提是知道 `EndpointId`——它一定会泄漏，是分享行为的副产品（你发出去的每一条链接里都带着它）。于是短 `basket_id` 意味着：你把链接发给 A，A 就能列出你全部的 basket，包括只打算给 B 的那些。查询还能在一条已建立的 QUIC 连接上开并发流批量试探，不是每次一个握手。128-bit 随机另有一个好处：不需要"本地查重"逻辑，撞了才是新闻。

**为什么文件字节交给 iroh-blobs。** 大文件需要断点续传、范围请求、边下边校验。iroh-blobs 已经做了，重写不划算。内容寻址在这里只是传输细节，不构成产品行为——见 ADR-0001 的非目标。

**为什么不做 token / 次数。**

- "1000 次"要么数请求，要么数人。数请求：同一个接收者清缓存、重装、换目录就能重复兑换，一个人就能刷爆，把它从一个凭证变成能打掉所有接收者的开关。数人：身份在 iroh 里是免费的（本地生成密钥对即可），数不出来。
- 次数限制防不住泄漏本身。慢速泄漏（一周一个人）碰不到阈值，而快速的大泄漏你本来就该手动吊销——花力气防你能察觉的那种、放过你察觉不到的，性价比是负的。
- indirection 的真价值是"不同接收者各有链接、可以单独吊销其中一条"，v1 用不上，而且是纯增量：加在同一个位置（用凭证换目录），不改数据模型。

**为什么限流不算访问控制。** 限流是运行时行为，随机 id 是结构属性。前者要求代码在每台机器、每种负载、每个版本上都正确；后者只要求发出去的链接是对的。而且按身份限流无效（身份免费）、按 IP 限流在走 relay 时不成立，剩下的全局限流会把机密性问题换成可用性问题——攻击者刷满限额就能让正常用户进不来。限流要做，但目的是保护创建者的资源。

## 后果

正面：

- 链接本身就是全部状态：没有映射表，没有凭证表。
- 吊销便宜：换 `basket_id`。
- 查看者侧几乎没有状态。

负面：

- 一个 basket 只有一条链接。"给不同人发不同链接、单独吊销其中一个"做不到，只能重建 basket。可接受：重建很便宜，cherry 是引用，不重新索引字节。
- 查看者的本地缓存键必须带 `endpoint_id`（`(endpoint_id, basket_id)`）：`basket_id` 只在创建者的命名空间内唯一，不同创建者之间会撞。

## 备选方案

1. **短位本地 hash（16 / 24 / 32 bit）** —— 弃。唯一性够，不可猜测性不够。
2. **token 兑换层 + 有效期 / 次数** —— 弃（v1）。将来要做 indirection 应该用无状态 AEAD token（`AEAD(owner_secret, {basket_id, label, issued_at})`）加一个只增的吊销集合，唯一的持久状态是本来就必须备份的 owner_secret。用持久化映射表做更差：重装一次所有已发出的链接全废。
3. **只带 `EndpointId`，不带完整地址** —— 弃。会让链接强依赖 n0 的 pkarr / DNS 解析服务。
4. **目录做成签名的 blob** —— 弃。在没有第三方转手的前提下，签名、版本号、缓存都没有对应的威胁。

## 重新评估的触发条件

- 出现"给不同接收者不同链接、单独吊销其中一条"的需求 → 加 token 层（无状态 AEAD + 吊销集合）。协议位置不变。
- 需要 `basket_id` 手抄或口述 → 加短别名层（别名映射到长 id），不要缩短 id 本身。
- 出现"目录要经第三方转手"的需求（也就是做种）→ 目录需要重新变成可独立验证的制品。
