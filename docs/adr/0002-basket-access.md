# ADR-0002: basket 的访问方式

- 状态: Accepted
- 日期: 2026-10-14
- 改动: 2026-10-15 重写。传输改成只读 NFS 导出（ADR-0007），链接里不再有 endpoint 地址，协议一节整个换掉。2026-10-16: `cherry list` 不再收 `--host` / `--ip`，每个篮子把名字和 IP 两条链接一起摆出来。

## 背景

访问一个 basket 要回答两件事：源在哪，以及看的是哪个 basket。ADR-0001 已经定了 basket 只有一个源、内容只能从它取。这里定链接形态和两者之间的协议。

## 决策

### 链接

分享的单位就是一个 link：

```rust
struct BasketLink {
    host: Host,             // 一个 IP，或者对方能解析的一个名字
    basket_id: [u8; 16],   // 128-bit 随机（CSPRNG）
}
```

内部文本形态是 `cherryshare:<host>:<32 位十六进制>`，IPv6 地址用方括号。这是控制响应中 `BasketLink` 的编码，不是浏览器入口，也没有对应的 `cherry mount` 命令。

`cherry list` 把它转换为网页链接 `http://<host>:20480/b/<32 位十六进制>/` 发给人。网页提供浏览、下载和 NFS 挂载命令。

- 内部编码不再借 `iroh-tickets`：解析时去掉 `cherryshare:`，再从右边切最后一个 `:`。
- 内部编码不带端口；网页 URL 必须带 HTTP 端口，默认 20480。NFS 端口固定 20490，写在挂载命令中（ADR-0007 决策五）。
- **名字和 IP 两条都摆出来让人挑**（2026-10-16 改；原来是 `list --ip` 切一条）。可用候选中本机名在前，局域网 IPv4 在后；取不到的就省略，不保证总有两条。IP 可能随 DHCP 变化，名字能否解析取决于对方的网络配置。
  - 名字来自 `gethostname`，不含点时补 `.local`，只是候选，不验证对方能否解析。Linux 上尤其取决于 mDNS 配置。
  - `.local` 通常依赖同一广播域里的 mDNS，不保证能跨路由或隧道。2026-10-17 实测：`ai-10-1-55-11-dev-sz.local` 从 10.1.2.x 解析不了，换成 IP 就通。
- 挂载命令不做「先判断再挂」（2026-10-17 定）。判断本身做得到——`mount | grep -F " on $MP "` 在 macOS 和 Linux 的输出上都命中，末尾那个空格还挡住了 `/x/foo` 与 `/x/foo/bar` 这种前缀误判——但重复挂载不是高频场景，而代价是那条命令长三倍、一眼看不明白，而它是要给人粘进终端的。真被 macOS 那句含糊的 `Operation not permitted` 耽误过再说。
- 主机名只收 ASCII 字母数字和 `-` `_` `.`，且不以 `-` 开头，因为会进入 shell 挂载命令。篮子名就是 `<名字>.basket` 的文件名，只排除空名和以 `.` 开头的；它进不了命令原文——挂载点那一段会先做投影（见下）。
- 链接里没有篮子名。挂载点那一段是现场拼的：`~/cherry/<篮子名>-<id 前 8 位>`（Linux 是 `/mnt/<同样的名字>`）。名字给人读，那 8 位防重名——挂载命令在对方机器上执行，我们不知道他那儿已经挂了什么。反过来，**Finder 里显示的是卷名**（NFS 取导出路径的最后一段，也就是完整 id），跟挂载点对不上，这个改不了。
- `basket_id` 是凭证，不是公开索引：谁拿到谁就能看。凭证写在篮子文件里（ADR-0008），所以吊销有两种：删掉那个文件，或者改 `id` 那行。删文件之后拿到过链接的人立刻打不开；只删掉文件里的路径行只是把篮子清空，旧链接仍然有效、以后再加内容也看得到。
- 一台机器可以持有任意多个 basket，各自独立的 `basket_id`。

### 访问方式

**同一份 basket 提供 NFS 和 HTTP 两个只读入口。** 管理操作只在本地：改数据目录里的 `.basket` 文件，或通过本机 local socket 读状态，不在 HTTP 上提供。

- NFS 挂载路径是 `host:/<32 位十六进制>`。MNT 验证篮子 id 后返回 file handle；根句柄直接含完整 id，子句柄是路径哈希。句柄同样是凭证，后续请求仍会查询篮子的当前定义（ADR-0007）。
- HTTP 的 `/b/<id>/` 提供页面，`/b/<id>/_api/list?path=...` 提供一个目录的 JSON，`/b/<id>/<路径>` 提供文件并支持 Range。目录或篮子根加 `?dl=zip` 流式打包；`_api/size?path=...` 计算有预算的目录大小。
- 所有上述 HTTP 入口都先检查篮子 id。单文件与 NFS 共用路径检查；zip 遍历跳过符号链接。服务端不保存内容副本。
- 顶层 `_` 前缀保留给网页资源和接口。以 `_` 开头的 cherry 可以加入、可以从 NFS 访问，但不能通过网页普通文件路径访问；普通隐藏文件不默认过滤。
- 当前两个网络监听都绑定 IPv4 的 `0.0.0.0`。链接类型能表示 IPv6，不代表当前服务提供 IPv6 监听。

### listing 的单位是**一个目录**，不是整棵树

（这一条原先写在 ADR-0006，那份已作废，决策本身还活着，挪到这里。）

- `dir` 为空 = 篮子根。否则是可见路径上的一个目录：虚拟目录（ADR-0009）只列点名的子项，真目录 cherry 和它里面的一次 `read_dir`，**不递归**。
- 可见路径可以有多段（ADR-0009）；网页 URL 和 NFS 里的路径就是这几段。
- 理由：NFS 的 `readdir` 本来就是按目录问的。整棵树意味着"为了显示一个目录要取回整棵树"。
- 文件的 size 和每条的 mtime 来自源文件元数据；目录 size 在 listing 中记 0，不递归统计。目录的 mtime 也是真的——客户端会拿它当缓存的新鲜度。每条还带着源文件的权限位，**照实报**（2026-10-17 改，原来一律报只读）：这些位会被对方机器上的 `cp`、`rsync -a`、`tar`、Finder 拖拽拿去当目标文件的权限，报成只读的话拷出来的一切都是只读的。列目录和问单个条目必须说同一句话。
- 篮子根和 `/./` 的中间层是**虚拟目录**（磁盘上没有对应物）。NFS 用那个 `<名字>.basket` 文件的 mtime 作为它们的 mtime；改文件里任何一行都会碰它，改源文件内容不会。

### 目录是响应，不是制品

服务端没有签名清单 blob、版本号或 listing 缓存。接收者仍有 NFS / 浏览器缓存，不能据此承诺每次看到的都是即时状态。

- **不需要签名**：内容只能从创建者那台机器取，中间没有第三方。
- **不需要版本号**：请求时现取就是最新的。
- **不维护离线目录**：网页列表 JSON 使用 `no-store`，但已打开的页面不会自动刷新。静态资源和单文件使用 `no-cache`，支持条件请求；目录大小另外缓存在浏览器标签页的 sessionStorage，刷新页面会清除，来回切目录可能复用旧数字。NFS 缓存由系统客户端管理，生成的命令给 `actimeo=5`。
- **没有文件监听器。** 触发点就是请求本身。而且监听器本身不可信（守护进程停过、事件队列会溢出、网络卷），任何监听器都必须配一个周期性重扫兜底，那就等于照样得写扫描缓存，监听器只把延迟从几秒缩到毫秒。它唯一多买的是延迟，而 ADR-0001 担心的是**无界的**陈旧。

## 非目标

- **不用短 id**（32-bit 一类的本地不重复 hash）。
- **不做 token 兑换层**（用外层 token 换真正的 `basket_id`）。
- **不做次数预算**（"这个链接最多被兑换 1000 次"）。
- **限流不作为访问控制**。
- **跨网不是场景**（2026-10-15 定）。隧道、端口转发、别的网段都不在范围里；IP 那条链接是给「同一层网里名字不灵」兜底的，不是跨网方案。

## 理由

**为什么 `basket_id` 是 128 bit。** 短 id 满足的是唯一性，这里真正需要的属性是**不可猜测性**——因为它是唯一的锁。主机地址不是秘密：它在链接里，也会被局域网扫描发现。所以一条链接的安全性完全落在这 16 个字节上。128-bit 随机另有一个好处：不需要"本地查重"逻辑，撞了才是新闻。

**为什么不做 token / 次数。**

- "1000 次"要么数请求，要么数人。数请求：同一个接收者清缓存、重装、换挂载点就能重复兑换，一个人就能刷爆，把它从一个凭证变成能打掉所有接收者的开关。数人：我们根本没有身份，数不出来。
- 次数限制防不住泄漏本身。慢速泄漏碰不到阈值；发现泄漏后要停掉分享，现在做得到：删掉那个 basket 文件，或者改掉 `id` 那一行（ADR-0008）。代价是整个篮子换凭证，不能单独吊销某一条链接。
- indirection 的真价值是"不同接收者各有链接、可以单独吊销其中一条"，v1 用不上，而且是纯增量：加在同一个位置（用凭证换挂载权），不改数据模型。

**为什么限流不算访问控制。** 限流是运行时行为，随机 id 是结构属性。前者要求代码在每台机器、每种负载、每个版本上都正确；后者只要求发出去的链接是对的。而且按身份限流无效（没有身份）、按 IP 限流在共享网络下会误伤，剩下的全局限流会把机密性问题换成可用性问题——攻击者刷满限额就能让正常用户进不来。当前网页限制打包并发为 2、大小计算并发为 6，不是通用请求限流，更不是访问控制。

## 后果

正面：

- 每个 basket 只持有一个随机 id；名字与 IP 链接共用它，没有按接收者维护的凭证表。
- 接收者不用维护 CherryShare 配置。NFS 的挂载和缓存由系统客户端管理，网页的目录大小与排序状态留在浏览器标签页。

负面：

- 一个 basket 只有一份凭证，即使名字与 IP 各有一条 URL，也不能单独吊销其中一条。换凭证是改 `.basket` 文件里 `id` 那一行，吊销是删掉那个文件（ADR-0008）；两种都会让这个篮子之前发出去的链接一起失效。
- 链接绑定在一个地址或名字上。IP 变化后旧 IP 链接可能失效；名字链接能否继续使用取决于名字解析。`cherry list` 提供候选，不做接收者侧连通性探测。
- 明文：当前 NFSv3 和 HTTP 都不加密。id 会出现在 URL、NFS 挂载路径和根句柄里，可能留在浏览器历史、挂载表和 shell history 中；只用于可信局域网。

## 备选方案

1. **短位本地 hash（16 / 24 / 32 bit）** —— 弃。唯一性够，不可猜测性不够，而这里是唯一的锁。
2. **token 兑换层 + 有效期 / 次数** —— 弃（v1）。将来要做 indirection 应该用无状态 AEAD token（`AEAD(owner_secret, {basket_id, label, issued_at})`）加一个只增的吊销集合。
3. **在内部 `cherryshare:` 编码中加入端口** —— 弃。NFS 固定端口见 ADR-0007；网页 URL 仍须显式写 HTTP 端口。
4. **目录做成签名的 blob** —— 弃。在没有第三方转手的前提下，签名、版本号、缓存都没有对应的威胁。

## 重新评估的触发条件

- 出现"给不同接收者不同链接、单独吊销其中一条"的需求 → 加 token 层（无状态 AEAD + 吊销集合）。协议位置不变。
- 需要 `basket_id` 手抄或口述 → 加短别名层（别名映射到长 id），不要缩短 id 本身。
- 出现"目录要经第三方转手"的需求（也就是做种）→ 目录需要重新变成可独立验证的制品。
