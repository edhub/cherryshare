# ADR-0003: 运行时模型

- 状态: Accepted
- 日期: 2026-10-14

## 背景

三条约束：

1. **分享的生命周期不能绑在任何交互端上**：敲完 `cherry add` 命令、终端关掉之后，别人还要能取。
2. **Unix 场景要能脱离图形界面运行**：用命令启动服务、配成 systemd 服务、用命令管理共享。
3. **挂载**是长时间、无 UI 的用法：要把远端 basket 暴露成本地目录。这一条现在落在内核的 NFS 客户端上（ADR-0007），不是我们自己写的适配器。

GUI v1 不做，见 ADR-0004。

## 决策

**一个常驻服务持有全部状态，其余一切都是客户端。**

### 服务独占什么

| 资源 | 为什么只能有一份 | 谁强制 |
| --- | --- | --- |
| NFS 导出的监听端口（固定 20490） | 一个端口只能有一个监听者 | 操作系统强制 |
| basket 配置与 BasketLink | 否则有两个写者 | 设计选择 |

这份清单就是"同一台机器上只能有一份的东西"。凡在此列，都归服务；其余进程只能通过它来操作。

### 服务怎么起来

只有一种启动方式：由系统拉起。Unix 用 systemd（前台手动跑就是直接运行 `cherryd`）；macOS 用 LaunchAgent（`SMAppService`）。

同一个仓库产出两个可执行文件：`cherry`（CLI）和 `cherryd`（服务）。v1 没有 GUI（ADR-0004），服务由系统拉起（macOS 上就是 LaunchAgent），不跟任何界面绑在一起。

原本还计划过一个独立的 `cherry-mount`，现在取消了：挂载由内核的 NFS 客户端做，我们这边没有任何平台相关的依赖要背（ADR-0007 决策七）。

客户端连不上服务时，能做的是给出明确的错误并**提示怎么把它拉起来**，而不是自己起一个进程内副本——否则就有两个持有状态的进程。

### 客户端

客户端只有一个：CLI。它通过 local socket 连服务。

| 客户端 | 消费什么 |
| --- | --- |
| CLI | 控制操作 |

- **CLI 必须能完成全部操作**，不是“给脚本用的子集”：创建 basket、放 cherry、取 BasketLink、列出、移除、看状态全都要靠它。（v1 没有 GUI，见 ADR-0004，所以这一条比以前更要紧。）
- **客户端不做语义判断。** 合法性、路径规范化、冲突、状态机只在 core / service 里存在一份；客户端只收集输入、呈现输出。**正因为交互端这么薄，才不存在"一个东西做两份"。**
- CLI 另外提供 `--json` 输出，那是给用户的脚本接口。

### 挂载这件事我们写哪一半

**创建者侧：** 把 basket 讲成只读 NFS，由对方的**内核**去挂。我们不写客户端，也不需要独立进程——它就在服务里。

**对方侧：完全不是我们的代码。** 对方跑的是他自己系统里那个现成的挂载命令，而这条命令由创建者这边的 `cherry link` 打出来：两个系统各一行（macOS 的 `mount_nfs`、Linux 的 `mount -t nfs`），粘一下就行。我们唯一提供的是一个字符串。

**所以 v1 没有“数据客户端”这一类东西。** 字节的路径是：对方的内核 → NFS → 创建者的服务 → 创建者磁盘上的那个文件。中间没有我们的进程。

（曾经有一个 `cherry mount <链接>` 子命令做这个“薄壳”。删了：它只是把一个现成的命令拼出来再跑一遍，而且只在一个系统上能跑——链接里本来就带着的那行命令已经够了，我们不多背一份平台差异。）

### 分层

```
cherry-core         basket 语义、listing（一个目录）
cherry-control      操作与响应的类型；客户端 / 服务端骨架
    ├── cherryd         服务（core + control 服务端 + 只读 NFS 导出）
    └── cherry          CLI 客户端
```

`cherry-control` 里的操作定义**不含传输细节**。v1 只把它挂到 local socket 上；将来要远程控制，再挑一个现成的传输挂上去，不用重写。

用 local socket 而不是 local HTTP 的理由见 ADR-0004「将来真要做的话」那三条里的第一条。

## 非目标

- **不做进一步的进程隔离**：服务内部的 core 与 socket 服务端在同一个进程里，所以 **core 崩 = 整个服务崩 = 分享中断**，core 必须自己稳。
- v1 不做远程控制：操作层预留位置，不实现。

## 后果

正面：

- 交互端薄到几乎没有可重复的逻辑。
- 关掉终端不影响分享；客户端崩了也不影响分享服务。
- 客户端侧仍然是“没有端口”的：CLI 只走 local socket，访问控制由 socket 文件权限（0600）完成。
- **但服务侧现在有一个端口**（NFS 导出）。它靠 `basket_id` 这个令牌把门，不再靠 socket 权限，暴露面是“端口可见、内容锁定”。这条按 ADR-0007 决策二来。

负面：

- **core 崩 = 分享中断。** 服务内部没有隔离，core 必须自己稳。
- 多了一条序列化边界（IPC 契约）。比 HTTP 那套小得多，但确实存在。
- 要处理服务生命周期：单实例、启动探测、崩溃后重新拉起、macOS 上安装 LaunchAgent。

## 未决问题

- **macOS 的路径授权**：需求不是"分享任意路径"，而是"分享用户显式选中的路径，访问不到就提示"。现在只有一个常驻服务去读文件，所以要验证权限提示以谁的名义弹出、服务能否用上用户在终端里已经获得的授权。
- **退出时的具体 UX**：是否开机自启。

## 重新评估的触发条件

- "core 崩 = 分享中断"变得不可接受 → 才需要把核心拆得更细。
- 出现远程控制需求 → 把 `cherry-control` 的操作层挂到某个现成的传输上（ADR-0007 决策六里的那个端口转发可以顺带干这件事）。不推翻本决策。
