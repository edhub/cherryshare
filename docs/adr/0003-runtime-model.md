# ADR-0003: 运行时模型

- 状态: Accepted
- 日期: 2026-10-14

## 背景

三条约束：

1. **分享的生命周期不能绑在 GUI 上**：用户 Cmd+Q 关掉 GUI 之后，别人还要能下载。
2. **Unix 场景要能脱离 GUI 运行**：用命令启动服务、配成 systemd 服务、用命令管理共享。
3. **挂载（未来）** 是长时间、无 UI 的用法，而且它要把远端 tap 暴露成本地目录。

UI 用什么做见 ADR-0004。

## 决策

**一个常驻服务持有全部状态，其余一切都是客户端。**

### 服务独占什么

| 资源 | 为什么只能有一份 | 谁强制 |
| --- | --- | --- |
| identity key / iroh endpoint | 同一个 key 只能有一个活跃 endpoint，否则 pkarr 记录与 relay 连接互相覆盖 | 协议强制 |
| blobs store（字节 + redb 索引） | redb 索引文件是排他锁 | 操作系统强制 |
| 索引缓存（`路径 → size/mtime/hash`） | 否则重复扫描、重复把一个 4 GB 文件 hash 两遍 | 设计选择 |
| tap 配置与 TapTicket | 否则有两个写者 | 设计选择 |

这份清单就是"同一台机器上只能有一份的东西"。凡在此列，都归服务；其余进程只能通过它来操作。

### 服务怎么起来

只有一种启动方式：由系统拉起。Unix 用 systemd（前台手动跑就是直接运行 `tearoom-service`）；macOS 用 LaunchAgent（`SMAppService`）。

同一个仓库产出三个可执行文件：`tearoom`（CLI）、`tearoom-service`（服务）、以及未来的 `tearoom-mount`。macOS 的 `.app` 里装 GUI 和 `tearoom-service` 两个，用户看到的仍是一个「Tearoom」。

GUI 连不上服务时，能做的是展示配置界面并**触发把它拉起来**，而不是自己起一个进程内副本——否则就有两个持有状态的进程。

### 客户端

三类客户端，全部通过 local socket 连服务：

| 客户端 | 有图形界面 | 消费什么 |
| --- | --- | --- |
| GUI | 是（唯一） | 控制操作 + 事件 |
| CLI | 否 | 控制操作 + 事件 |
| mount | 否。它是适配器，不是界面 | **数据**：listing + 按范围读字节（流式） |

- **CLI 必须能完成全部操作**，不是"给脚本用的子集"：Unix 上没有 GUI，创建 tap、加条目、取 TapTicket、列出、移除、看状态全都要靠它。
- **GUI 与 CLI 是兄弟，不是父子。** GUI 不通过 CLI 中转——那等于把文本格式当成类型协议，还要为事件推送再造一个常驻流模式。
- **客户端不做语义判断。** 合法性、路径规范化、冲突、状态机只在 core / service 里存在一份；客户端只收集输入、呈现输出。**正因为交互端这么薄，才不存在"一个东西做两份"。**
- CLI 另外提供 `--json` 输出，那是给用户的脚本接口，不是 GUI 的后端。

### mount 是数据客户端

`tearoom-mount` 是独立二进制——它要背 macFUSE / FUSE-T 那堆重且平台相关的依赖，主程序不该有。它不持有状态，数据全部向服务要。

理由**不是**"store 只能有一个写者"（mount 只读，什么都不写）。硬理由是服务独占字节缓存；软理由是缓存会分裂、传输会变得不可见、配置与凭证的权威在服务、以及挂载本机 tap 时内容本来就在服务的 store 里。所以独立 mount 技术上可行，只是要重复付这些代价。

**服务侧必须做块级缓存与预读，协议也必须支持流式 range 读。** 这不是优化：文件系统的读是小块、同步的，每次一个 socket 往返再加一次网络取数会慢到不可用；而调用方（`ls`、Finder）没有超时，卡住就是把它们挂死。

### 分层

```
tearoom-core        tap 语义、扫描与索引、iroh、store
tearoom-control     操作与事件的类型；客户端 / 服务端骨架
    ├── service       core + control 服务端
    ├── GUI 客户端
    ├── CLI 客户端
    └── mount 客户端
```

`tearoom-control` 里的操作定义**不含传输细节**。v1 只把它挂到 local socket 上；将来要远程控制，同一个操作层再挂到一个 iroh ALPN（带控制 key）上，不用重写。

用 local socket 而不是 local HTTP 的理由见 ADR-0004 的备选方案。

## 非目标

- **不做进一步的进程隔离**：服务内部的 core 与 socket 服务端在同一个进程里，所以 **core 崩 = 整个服务崩 = 分享中断**，core 必须自己稳。（GUI 与 mount 是独立进程，它们崩了不影响分享——这一层隔离已经有了。）
- v1 不做远程控制：操作层预留位置，不实现。

## 后果

正面：

- 交互端薄到几乎没有可重复的逻辑。
- Cmd+Q 退出 GUI 不影响分享；客户端崩了也不影响分享服务。
- 没有端口，所以没有 DNS rebinding / CSRF / token / 绑错地址那一整类问题；访问控制由 socket 文件权限（0600）完成。

负面：

- **core 崩 = 分享中断。** 服务内部没有隔离，core 必须自己稳。
- 多了一条序列化边界（IPC 契约）。比 HTTP 那套小得多，但确实存在。
- 要处理服务生命周期：单实例、启动探测、崩溃后重新拉起、macOS 上安装 LaunchAgent。

## 未决问题

- **macOS 的路径授权**：需求不是"分享任意路径"，而是"分享用户显式选中的路径，访问不到就提示"。现在只有一个常驻服务去读文件，所以要验证权限提示以谁的名义弹出、服务能否用上 GUI 已经获得的授权。
- **退出时的具体 UX**：是否常驻菜单栏、是否开机自启。
- **local socket 的具体协议**：编码、帧格式、事件推送方式。
- **identity key 的导出与恢复**：它是所有已发出 TapTicket 的锚点——丢了 key，旧链接全部失效（地址指向一个不再存在的 endpoint）。换机、重装、备份都要能带过去。

## 重新评估的触发条件

- "core 崩 = 分享中断"变得不可接受 → 才需要把核心拆得更细。
- 出现远程控制需求 → 把 `tearoom-control` 的操作层挂到 iroh ALPN 上。不推翻本决策。
