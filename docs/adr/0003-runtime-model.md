# ADR-0003: 运行时模型

- 状态: Accepted
- 日期: 2026-10-14

## 背景

三条约束：

1. **分享的生命周期不能绑在任何交互端上**：写完篮子文件、终端关掉之后，别人还要能取。
2. **Unix 场景要能脱离图形界面运行**：用命令启动服务、配成 systemd 服务、用命令管理共享。
3. **挂载**是长时间、无 UI 的用法：要把远端 basket 暴露成本地目录。这一条现在落在内核的 NFS 客户端上（ADR-0007），不是我们自己写的适配器。

原生管理 GUI 暂不做；接收者已有浏览和下载网页，见 ADR-0004。

## 决策

**一个常驻服务持有全部状态，其余一切都是客户端。**

### 服务独占什么

| 资源 | 为什么只能有一份 | 谁强制 |
| --- | --- | --- |
| NFS 监听端口（20490）、HTTP 监听端口（默认 20480） | 同一个监听地址不能重复绑定 | 操作系统强制 |
| basket 配置与 BasketLink | 否则有两个写者 | 设计选择 |

正常使用只运行一个服务。当前没有数据目录锁；端口绑定失败也不会阻止服务启动，所以不要让两个进程共用同一数据目录。

### 服务怎么起来

同一个仓库产出 `cherry`（CLI）和 `cherryd`（服务）。可以直接前台运行 `cherryd`，也可以用发布包的 `bash install.sh` 安装常驻服务：macOS 写 LaunchAgent plist 后用 `launchctl` 加载；Linux 写 systemd user unit，不使用 `SMAppService`。

macOS 登录时启动。Linux 安装时启用 user unit，并尝试开启 linger；失败会提示，未开启时注销后服务可能停止。两边均配置异常退出后重启，不跟终端或浏览器的生命周期绑定。

原本还计划过一个独立的 `cherry-mount`，现在取消了：挂载由内核的 NFS 客户端做，我们这边没有任何平台相关的依赖要背（ADR-0007 决策七）。

客户端连不上服务时，能做的是给出明确的错误并**提示怎么把它拉起来**，而不是自己起一个进程内副本——否则就有两个持有状态的进程。

### 客户端

管理客户端只有 CLI，通过 local socket 连服务。接收者的浏览器走 HTTP，系统 NFS 客户端走 NFS；这两条入口不提供管理操作。

| 客户端 | 消费什么 |
| --- | --- |
| CLI | 控制操作 |

- 当前只有读命令：`list`（网页链接）、`show`、`status`。写是直接改数据目录里的 `.basket` 文件（ADR-0008），所以没有 `new` / `add` / `rm`，也没有 `--json` 输出。
- **服务端负责语义校验。** CLI 把路径按自己的工作目录规范化成绝对路径，服务端再次校验；源文件名、冲突和状态都由 core / service 判断。

### 挂载这件事我们写哪一半

**创建者侧：** 把 basket 讲成只读 NFS，由对方的**内核**去挂。我们不写客户端，也不需要独立进程——它就在服务里。

**对方侧的挂载不是我们的代码。** 网页提供两个系统的命令（macOS 的 `mount_nfs`、Linux 的 `mount -t nfs`），接收者复制后在终端执行。CLI 只输出网页链接，不再输出挂载命令。

NFS 读请求由对方内核发到 `cherryd`，服务读取源文件后返回字节。接收者没有 CherryShare 进程。网页下载则由浏览器直接向同一服务请求文件或流式 zip。

原来的 `cherry mount <链接>` 子命令已经删除；挂载命令统一在网页提供。

### 分层

```
cherry-core         basket 语义、listing（一个目录）
cherry-control      操作与响应的类型；客户端 / 服务端骨架
    ├── cherryd         服务（core + control 服务端 + NFS + HTTP）
    └── cherry          CLI 客户端
```

`cherry-control` 里的操作定义**不含传输细节**。v1 只把它挂到 local socket 上；将来要远程控制，再挑一个现成的传输挂上去，不用重写。

管理操作用 local socket 而不是 local HTTP 的理由，见 ADR-0004「将来做原生管理 GUI 时」。

## 非目标

- **不做进一步的进程隔离**：服务内部的 core 与 socket 服务端在同一个进程里，所以 **core 崩 = 整个服务崩 = 分享中断**，core 必须自己稳。
- v1 不做远程控制：操作层预留位置，不实现。

## 后果

正面：

- 交互端薄到几乎没有可重复的逻辑。
- 系统托管时，关掉 CLI 终端不影响分享；客户端崩了也不影响服务。前台运行 `cherryd` 时仍要保持服务进程存活。
- 客户端侧仍然是“没有端口”的：CLI 只走 local socket，访问控制由 socket 文件权限（0600）完成。
- **服务侧监听两个 IPv4 网络端口**（NFS 和 HTTP，均绑定 `0.0.0.0`），共享内容靠 `basket_id` 限制访问。两者都不加密；HTTP 不暴露 local socket 的管理操作（ADR-0002、ADR-0004）。

负面：

- **core 崩 = 分享中断。** 服务内部没有隔离，core 必须自己稳。
- 多了一条序列化边界（IPC 契约）。比 HTTP 那套小得多，但确实存在。
- 要处理服务生命周期：单实例、启动探测、崩溃后重新拉起、macOS 上安装 LaunchAgent。

## 未决问题

- **macOS 的路径授权**：需求不是"分享任意路径"，而是"分享用户显式选中的路径，访问不到就提示"。现在只有一个常驻服务去读文件，所以要验证权限提示以谁的名义弹出、服务能否用上用户在终端里已经获得的授权。
- **单实例保护**：目前靠部署时只启动一份，尚无数据目录锁。

## 重新评估的触发条件

- "core 崩 = 分享中断"变得不可接受 → 才需要把核心拆得更细。
- 出现远程控制需求 → 把 `cherry-control` 的操作层挂到某个现成的传输上（ADR-0007 决策六里的那个端口转发可以顺带干这件事）。不推翻本决策。
