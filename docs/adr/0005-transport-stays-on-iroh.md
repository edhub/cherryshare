# ADR-0005: 传输层留在 iroh / QUIC 上

- 状态: Accepted
- 日期: 2026-10-15

## 前提

沿用 ADR-0001 的两条：**自用、小范围、局域网优先**；以及**不允许静默失败 + 可恢复优先于可理解**。

## 背景

iroh 用的是**用户态** QUIC。内核只看到一个不透明的 UDP 套接字，于是每个包都要走一遍：

```
内核收包 → 拷到用户态 → 解析 QUIC 头 → 解密 → 处理 ACK → 拥塞控制记账
        → 流重组 → 加锁 → … → 加密 → 组装头 → 拷回内核 → 发包
```

实测（完整数据见 [`../performance.md`](../performance.md)）：

- **每包固定成本约 44µs**（两端合计），是健康 QUIC 的 20~40 倍。
- 归因：`__sendmsg` + `__recvmsg` 占发送端 **57.6%**、接收端 **42.4%**。
  锁竞争（0.7%）、AEAD（0.8%）、BLAKE3（3.2%）、磁盘（1.1%）全部可排除。
- 在普通的 1500 MTU 链路上，这等于**每核只能处理约 27 MB/s**。

而**内核 TCP 在同一台机器上（loopback）能跑 7.7 GB/s**，看起来差 135 倍。

**但那 135 倍是 loopback 的假象**：loopback 上没有网线，TCP 只是内核 memcpy。
真实链路上（Mac ↔ Orange Pi 走 WiFi）：

| | 吞吐 |
|---|---|
| TCP 单流（对端写 `/dev/null`） | 16.9 MB/s |
| cherry（对端写盘 + 校验） | 11.3 MB/s |

**约 1.5×，而且那 1.5× 不是 CPU 造成的**——Pi 最忙的核只有 6~12%。

## 决策

**不自己写传输层。留在 iroh / QUIC 上。**

## 理由

1. **换传输层买不到那 1.5×。** 它不是 CPU 造成的，而是 Cubic 在丢包链路上的行为——
   换掉传输层并不能保证解决，反而会换一个未知数。
2. **自研传输层要重写一整套**：分块、BLAKE3 校验、range 请求、断点记账、线协议。
   ADR-0001 说"可恢复优先于可理解"，而断点续传正是靠 iroh-blobs 的内容寻址
   **在结构上**保证的，不是靠我们写对。
3. **会丢掉**：endpoint 身份、打洞、relay 兜底，以及 ADR-0002 的
   `BasketLink = EndpointAddr + basket_id` 整套模型。

## 什么时候该重新考虑

触发条件，写在这里以免重新从零论证一遍：

- **出现 ≥500 Mbit/s 的链路**（千兆有线、或开了 jumbo frame 的局域网）。
  那时用户态的 ~27 MB/s/核 才会成为第一个瓶颈，内核 TCP 的优势才真正兑现。
- **上游暴露了 `max_udp_payload_size`**，或修好了逐包成本 → 见下表的 MTU 与"逐包"两条。
- **上游给出一个真正可用的 TCP / 自定义数据路径。**

## 刻意没有做

- **自研 TCP 传输层。**
- **QUIC-over-TCP。** iroh 的 `unstable-custom-transports` 抽象边界是**数据报**
  （`CustomSender::poll_send` 收 `&Transmit`）——它替换的是 UDP 套接字，**QUIC 还是照跑**，
  用户态开销一分不省，还要额外付 TCP 成帧和队头阻塞。它真正服务的场景是非 IP 路径
  （内存、UNIX 套接字、Tor、蓝牙）。
- **把 `unstable-custom-transports` 当成"换掉 QUIC"的入口。**

## 已知的天花板与杠杆

| 杠杆 | 实测结果 | 现状 |
|---|---|---|
| **MTU 发现上限** | 高 MTU 链路上 **+4.7× 吞吐、CPU −16%** | iroh 把它锁在 1452 且未暴露 → 只能提上游 |
| **ACK 频率** | loopback 上 **+31% 吞吐、CPU −22%** | 待丢包链路验证后才考虑进默认值 |
| 多连接 / 多流 | **无效**（N=8 反而 −25%） | 已排除 |
| GSO / Apple fast path | **+8.9%**，而接收端 CPU +32% | 不值得 |
| 拥塞控制（BBR3） | 本链路无优势 | 已排除 |
| 逐包开销本身 | `__sendmsg` / `__recvmsg` | 上游的事 |

**结论：吞吐的天花板是用户态 QUIC 的逐包成本，而这不是我们这个仓库能改的东西。**
能做的只有减少包数（MTU、ACK）和接受它。
