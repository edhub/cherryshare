# ADR-0006: mount 的数据路径

- 状态: Accepted
- 日期: 2026-10-15

**本决策改动了两处已有决策**：ADR-0002 的「协议」一节（listing 的单位从「整棵树」改成「一个目录」，原语从两个变成四个），以及索引里 listing 的定义。两处都在文中标明。

## 前提

沿用 ADR-0001 的前提：自用、小范围、局域网优先；**不允许静默失败**；**可恢复优先于可理解**。

再加一条只对这里成立的前提：**mount 是读取点，不是镜像。**

## 背景

ADR-0003 已经把 mount 定性成「数据客户端」，并且要求：**服务侧必须做块级缓存与预读，协议必须支持流式 range 读**（原话：「这不是优化」——因为文件系统的读是小块、同步的，而调用方没有超时）。

那份 ADR 没定的是三件事：**listing 的单位**、**读的原语**、**缓存活多久**。这里定它们。

## 决策

### 一、mount 是读取点，不是镜像

这一条 ADR-0001 其实已经定了，只是没落到 mount 上：**共享语义是引用（live index），不是快照**；创建者是唯一源，**创建者不在线 basket 就不可用**；而「做种 / 常驻缓存节点 / 可用性广播」和「离线可用性」都在刻意没有做的清单里。

所以 mount **不是**「把 basket 同步到本地」：

| | 镜像（带缓存的副本）| **读取点（本决策）** |
| --- | --- | --- |
| 本地有「这个文件」吗 | 有，缓存即副本 | **没有**。文件是远端的一段字节 |
| 缓存的地位 | 语义的一部分（「我已经有了」）| **纯实现细节**（为了不重复付流量）|
| 目录内容 | 本地同步后的状态 | **每次现算** |
| 离线 | 缓存过的能用 | 用不了——这是定位，不是缺陷 |
| 用户心智 | 「这盘是我的」| **「这盘是别人的，我只在看」** |

### 二、listing 的单位是**一个目录**，不是整棵树 —— 改 ADR-0002

ADR-0002 现在是 `GetListing(basket_id)` 返回整棵树的扁平表 `[(路径, size, mtime)]`。改成按目录，原语跟着换。

理由：

- **FUSE 的 `readdir` 本来就是按目录的。** 整棵树对 mount 是错形状——**为了显示一个目录，要取回整棵树**。
- 代价从 **O(树)** 变成 **O(一个目录)**，而且是**需求驱动**的：GUI 展开到哪列到哪，Finder 打开哪个文件夹列哪个。
- 这是 FTP 的形状（`LIST` 就是列一个目录），而它经得起时间考验。

**这不改变 ADR-0002 的论证**：那里说 listing「耗时只与 cherry 数量有关，与内容变了多少无关」，讲的是**与内容无关**。改成按目录只是把这个常数压到一个目录。

### 三、四个原语

```
ListDir { basket_id, dir }     → [(name, kind, size, mtime)]   一次 readdir + 每个 entry 一次 stat
Lookup  { basket_id, path }    → (kind, size, mtime)           一次 stat，不逐级走
Open    { basket_id, path }    → hash                          之后按 hash 读
Read    { hash, offset, len }  → bytes                         命中缓存 / 缺哪块取哪块
```

`Lookup` 是 O(1)：创建者直接 `stat(cherry 的根 + 相对路径)`，不需要逐级 `readdir`。

`Read` 按 hash 而不是按路径——**路径到 hash 的解析只发生在 `Open`**，这一条是下一节的前提。

### 四、有效性靠**事件**，不靠时钟

一条缓存（目录条目、查找结果、块）**没有 TTL**。它有效，直到两件事之一发生：

1. **出现新的请求** —— 客户端再问一次，就重新问创建者。
2. **用它的时候出错** —— 失效，下次请求重取。

对打开的文件，这正是 POSIX 的语义，也正是 ADR-0001 已经写过的（「接收方下载到的是一次性副本，创建者后续的修改不会推送过去」）：

```
open(path)  ← 那次「请求」：lookup 一次，记住 (hash, size, mtime)
   read(…)  ← 全部走那个 hash，不再回头检查
 close

open(path)  ← 新的请求 → 重新 lookup → 可能拿到新版本
```

**于是「没有人看的时候，索引新不新没有意义」这条 ADR-0002 的判断从 listing 推广到了字节。**

**硬约束：`open` 必须重新 lookup。** 不能靠内核缓存的 dentry 直接拿旧 hash。否则：

```
创建者改了 a.mp4        → 新 hash
我这边还拿着旧 hash     → 旧字节可能还在创建者 store 里
                        → 我们【成功地】返回旧内容 ← 没有报错可触发
```

**那正是 ADR-0001 最怕的静默陈旧**（「展示一份陈旧的列表让人以为文件还在」）。「出错就失效」纠正不了它，因为这里根本没出错。所以 `entry_timeout` 不能报大。

**这套「正确性靠出错」能成立，是因为内容寻址**：bao 逐块校验，**我们永远不可能返回错字节，最坏是取不到**——错误是干净、可判定的。没有校验的话，这就是在赌内容对不对。

**推论：错误变成承重的了。** 所以错误必须可区分（「过期了」vs「真的没有」）、不许被吞（`provider.rs` 已经把内部错误包成 `WireResponse::Error` 回给客户端）、**不许变粘**（一次失败不能被缓存成「这个文件没了」）。

### 五、缓存

缓存就是**服务那个唯一的 store**（ADR-0003：服务独占 blobs store）。不另起一层——另起一层要重做校验、索引、去重，白付。

**块粒度**：校验粒度是 BLAKE3 chunk = 1KB（协议定死）；**取数单位是我们选的策略**，建议 1MB 对齐。一条 1KB 的 range 请求等于一次网络往返，不可接受。

**上限可配**（如 1G / 5G）。三个要点：

| | |
| --- | --- |
| **记账用实占字节** | 不能用 `ls` 的长度。**随机读会造稀疏文件**——读一个 1GB 文件的尾部，`ls` 显示 1GB 而实占几 MB |
| **淘汰顺序** | LRU，按「最后一次被读」 |
| **两类永不淘汰** | ① 有 share tag 的（用户的东西）② **正在被读的**（`TempTag` 保护）|

第二条之所以敢做，是因为**缓存不参与语义**：它是远端内容的副本，删掉只是重新付流量，**不丢数据**。所以淘汰规则可以又笨又激进——LRU 行，「卸载就清空」也行。

**注意这一条与 ADR-0001 并不冲突。** 那里说「store 里没有只此一份的数据」，讲的是**正确性**（删了不丢什么）；mount 的缓存同样满足。变的只是 store 从「只增」变成「会涨」，需要一个**空间**策略，不是一个**正确性**策略。

**预读**：服务端能看到读偏移，所以判断得了顺序访问。未命中取 `[对齐(start) .. 对齐(end) + 1 块]`，连续命中后窗口翻倍（跟内核 `readahead` 一个路子）。**不做**按文件类型的智能预读。

### 六、索引缓存（ADR-0002 已要求，实现要补）

ADR-0002 的「协议」一节已经写了这个，而**代码里没有**：

> `GetFile` 才做昂贵的部分——拿 `size + mtime` 与持久化的索引缓存比对，没变就命中缓存，变了才读文件算 hash。
>
> **持久化的索引缓存（`路径 → size/mtime/hash`）是必需的：没有它，比对这一步就退化成「读一遍所有内容」。**

现状是 `hash_file` 每次都走 `store.blobs().add_path(path)`——**克隆 + 读整个文件算 hash**。一个 4GB 文件取两次就 hash 两遍，两个人各取一次也两遍。mount 会把这个放大。

落地形态：

```
(path) → (size, mtime, hash)      持久化在服务侧（不进 listing）
用的时候先 stat 比 (size, mtime)
  对得上 → 直接用缓存的 hash
  对不上 → 条目作废（丢掉，不是立刻重算）
```

**失效 = 丢条目，重算 = 请求时。** 没有「改了但还没重算」的中间状态。

## 刻意没有做

- **不做镜像 / 快照 / 离线可用。** 见决策一，那是 ADR-0001 已经否掉的。
- **不做文件监听器。** 理由不是「触发点是请求本身」那么简略，而是：① 索引缓存让「比对」变成一次 stat，监听器没有用武之地；② **监听器本身不可信**——守护进程停过、事件队列溢出（inotify `max_user_watches`、FSEvents 会丢事件）、网络卷，所以任何监听器**都必须配一个周期性重扫兜底**，也就是说你照样得写扫描缓存，监听器只把延迟从 TTL 缩到毫秒；③ 它唯一多买的是延迟，而 ADR-0001 担心的是**无界的**陈旧。
- **不做整棵树 listing。** 见决策二。
- **不把 FUSE 的具体 TTL、预读窗口、块大小写死在这里** —— 见未决问题。

## 后果

正面：

- **一个原语，没有第二条路**：GUI 和 mount 都是「展开到哪、列到哪」。
- **不需要监听器，也不需要 TTL 扫描缓存**——freshness 的问题在结构上消失了，不是被绕过。
- 打开文件后**读路径完全稳定**（一个 hash 到底），没有「读到一半版本变了」。
- 缓存可以随时清，**不影响正确性**。

负面：

- **`open` 必须重新 lookup**，这条约束得在 mount 里真正落实，漏了就是静默陈旧。
- **错误变成承重的**：失效与重取的链路必须可靠，否则要么卡死要么误导。
- 首次读一个文件要付一次网络往返（创建者算 hash + 取数），**必须有明确的状态**（ADR-0002 已有的要求）。
- store 从「只增」变成「会涨」，多了一个空间策略要维护。

## 未决问题

- **FUSE 的具体 TTL 组合**：`entry_timeout` 要小（决策四的硬约束），`attr_timeout` 可以大一些（它只影响显示的 size/mtime，真正的读按 open 时的 hash 走）。具体数值、预读窗口、块大小——留到 `docs/mount.md`。
- **macFUSE / FUSE-T 的选型**，以及 ADR-0003 已列的挂载机制那一堆。
- **缓存上限的默认值**，以及 `cherry status` 怎么呈现（要用实占口径）。
- **`ListDir` 的 `kind` 是否需要区分符号链接**。

## 重新评估的触发条件

- 出现「离线也要能看」的需求 → 那是 ADR-0001 级的改动（等于要做种），不是本决策的修补。
- 首次读的等待变成抱怨 → 先调预读与取数单位，再考虑「整棵树预热」这种准镜像行为。
- 需要多作者（多源）→ 本决策整个作废，重新来过。
