# ADR-0007: 局域网这条主路走只读 NFS 导出

- 状态: Accepted
- 日期: 2026-10-15

## 背景

原本的设计是：创建者用 iroh 把字节发出去，接收侧再挂成本地目录。走到实现阶段发现这个组合在主打场景里不成立。

**主打场景是局域网。** 而局域网里已经有一个成熟的东西在干同一件事：SMB / 文件共享。它零安装、文件系统完整、客户端到处都有。我们写的挂载没有一项比得过它。

**iroh 真正解决的问题只有一个：在没有可达 IP 路径时不用配置、不用账号就能连上。** 局域网里 IP 路径本来就有，所以它的活是空的。而它带来的代价是整套东西：endpoint、blobs store、内容寻址、索引缓存、按范围读、缓存上限与淘汰。这些全都是"用 iroh-blobs 给挂载做传输"的副产品，不是产品要解决的问题。

反过来看，有一个好处我们之前完全没算进去：**对方什么都不用装。** 而拿到这个好处并不需要 iroh——只要让创建者讲一个内核本来就懂的协议。

## 决策

### 一、传输是创建者侧的一个只读 NFS 导出

创建者的服务在本机把 basket 导出成 NFS，对方的系统自带客户端直接挂。我们不写任何客户端。

理由不是"NFS 比 iroh 快"，而是**内核自带的 NFS 客户端把难的部分都做了**：元数据和数据的缓存与淘汰、预读、超时与重试、挂载/卸载、Finder 集成。用 FUSE 做这些要自己写，而 macOS 上 macFUSE 要 kext、FUSE-T 本身就是在**本机跑一个 NFS 服务再挂回环**——既然它都是这么干的，我们直接讲 NFS 就少一层依赖。

服务端用 `nfsserve`（Rust，NFSv3，纯用户态）。它不是玩具：Hugging Face 的 `hf-mount` 就是用它把远端数据集挂成本地只读文件系统，形态和我们完全一样。

实测（macOS 27，本机回环，256 MiB）：冷读 747 MB/s（服务端还是 debug 版）、再读一次 16 GB/s（全在内核 page cache 里，根本没到服务端）、字节与源文件逐字节一致；挂载不需要 root；服务端被杀之后读未缓存的字节报 `Operation timed out`，**不卡死**（默认 `timeo=10,retrans=10` 下约 8 秒）。

### 二、权限模型是能力令牌，不是账号

`basket_id` 是 128 位随机数，它作为**挂载路径的第一段**：`host:/<32 位十六进制>`。不知道 id 就挂不上。

这条只在挂载那一刻判一次（NFS 的 MNT 请求），此后客户端拿的是一个不透明的 file handle，协议里不再出现 id。

**`path_to_id` 必须拒绝 `"/"`。** 这是这个设计成立的前提，不是细节：全局根一旦交出去，客户端 `readdir` 一下就能枚举出所有 basket_id，"密码"就白设了。同理 `lookup` 里的 `".."` 不能返回全局根。

没有任何形式的账号、成员表、登录。**"知道 id"就等于"有权限"**，这和 ADR-0002 里 `basket_id` 的定位一致，只是到这里它才真的被强制执行。

### 三、只读

所有写操作（`setattr` / `write` / `create` / `mkdir` / `remove` / `rename` / `symlink`）一律拒。

属性上不透创建者的身份：uid/gid 报 0，写位一律清掉（这个导出不接受写，报可写就是骗客户端），size 和 mtime 报真实值。**执行位照实报**——共享一包可执行文件是正经用例，把二进制报成 `0o444` 的话对方 `cp` 出来就跑不起来。篮子根是虚拟目录，它那层 mtime 用篮子定义那个配置文件（`baskets.json`）的 mtime，那也是真实的。共享出去的是一份内容，不是那台机器的延伸。

### 四、只共享真文件和真目录

`..` 和符号链接**都不许穿过**，它们是同一个边界的两半。共享目录里出现符号链接时跳过它并警告；如果按名字直接去读，明确的报错，不是静默跟随。

没有这条，共享一个目录就等于共享那个链接指向的任何东西。

### 五、端口固定，不进链接

固定 `20490`。这样链接的格式不用动，也省掉"端口是多少"这个要传的信息。端口被占是**启动时的响亮失败**（有明确的错误信息），不是静默失败。

### 六、iroh 整套删掉，需要通道时再加回来的是一个**端口转发**

现在删掉：endpoint、blobs store、自研 ALPN、内容寻址、索引缓存、按范围读、缓存上限与淘汰。它们全都是为"iroh 传字节给挂载"服务的，那条路没了，它们就没有消费者。

将来真的需要跨网时，加回来的东西**是一个 TCP 端口转发**（本机监听 → 隧道 → 对端的 20490），不是一套新的数据协议。NFS 只用一个端口（客户端带上 `port=` 和 `mountport=` 就不需要 portmapper），所以一个转发器就够。到那时 NFS 协议端到端地跑在隧道上，而**创建者侧的文件服务逻辑一行都不用改**。

ADR-0005 里那条仍然成立的内核结论保留在这句话里：**不自己写传输层**，跨网也用现成的。

（2026-10-15 定：**跨网不是场景**。这一段留着只说明“真要加也不是换协议”，不作为路线。）

### 七、分享单位不变，但挂载这件事我们一行代码都不写

basket 仍是分享单位，链接仍是那一条字符串，内容是 `host + basket_id`。

对方那边什么代码都不用装。挂载命令由创建者这边打出来——**两个系统各一行**（macOS 是 `mount_nfs -o nolocks,...`，Linux 是 `sudo mount -t nfs -o nolock,...`），对方粘一下。两边的选项名不一样（多不多一个 s），Linux 还要 root，所以两行都得给：我们不知道对方是什么机器。

**`cherry-mount` 这个独立二进制取消，CLI 里那个 `cherry mount <链接>` 子命令也删了。** 前者原本存在的理由是"要背 macFUSE / FUSE-T 那堆重且平台相关的依赖"，而现在挂载由内核的 NFS 客户端做，我们这边没有平台依赖要背；后者只是把一个现成的命令拼出来再跑一遍，而链接里本来就带着那行命令。留着它就要为每个系统各维护一份差异，不值。

## 非目标

- **不做账号 / 成员表 / 登录。** 能力令牌就够了，见决策二。
- **不做 SMB。** 它需要凭证或访客配置，而 id 已经是凭证；实现成本也比 NFSv3 高一个量级。
- **不缩短 `basket_id`。** 它要的是不可猜测性，不是唯一性。
- **不自研传输层。** 包括不做 QUIC-over-TCP 那种"看起来像自研"的绕路。
- **不做服务端缓存。** 创建者直接把磁盘上的文件读给对方，中间没有副本要管；对方那边的缓存由内核管。
- **不做跨网。** 那是将来加一个端口转发的事，不是现在。

## 后果

正面：

- **对方零安装。** macOS、Linux 自带 NFS 客户端；Finder 里就是一个普通目录，能浏览、能预览、能拖拽复制。
- 代码量小得多：没有 store、没有内容寻址、没有缓存上限与淘汰、没有传输协议。服务端只剩"把 basket 讲成 NFS"这一层适配。
- 没有 store 的生命周期问题（上限、淘汰、保护、以及"分享的文件被复制进 store"）。创建者读的就是用户自己的文件。
- 失败是响亮的：挂不上、超时、写入被拒都有明确错误，不会静默陈旧。

负面：

- **只有同一个局域网能用。** 这是这条路的根本限制。（跨网不是场景，2026-10-15。）
- **没有任何认证强度。** id 在局域网里是明文传的（NFSv3 不加密），会留在对方的挂载表和 shell history 里。这是能力式链接的通病，家里和办公网可以接受，公共 WiFi 上不行。
- **创建者开了一个网络监听。** 暴露面是"端口可见、内容锁定"。ADR-0003 里"没有端口所以没有 DNS rebinding / CSRF / token / 绑错地址那一整类问题"这句话从此不再成立。
- **Windows Home 没有 NFS 客户端**（Pro 才有），所以"零安装"在 Windows 上不成立。
- 目录列表的可见延迟由客户端的属性缓存决定（挂载命令里给的是 `actimeo=5`）：创建者增删一颗 cherry，对方最多 5 秒后看见。
- **服务重启对对方是透明的**（实测）：fileid 是路径的哈希，句柄就用它；篮子根另一种形态，把 128 位篮子 id 直接放进去——因为它是新进程里唯一必须能被“冷”解析的。所以 `ls` 挂载根、`ls` 子目录、`df` 从重启后的第一秒起就是好的；碰到客户端缓存里那些**子句柄**时会报一次 `Stale NFS file handle`，但客户端会自己按名字重新 lookup，**实测两三秒后就全好了**（整棵树 `diff -r` 无差异，不用重挂）。
- **但已经打开、正在读写的文件跑不掉**：那个句柄被进程握着，重启后报错，只能关掉重开（跑到一半的 `cp` / `rsync` 得重来）。这是这套句柄方案的天花板：非根句柄不可逆（哈希），所以新进程没法替一条冷句柄反推出路径。要再进一步就得把句柄里塞路径（64 字节放不下深路径），或者启动时走一遍整棵树——两条都不值。
- **挂载点里的文件不能直接执行**（`./x.sh` 报 `bad interpreter: Permission denied`，连 signed 的二进制也一样）。这是 NFS 客户端那边的规矩，与服务端怎么报权限位无关，加 `-o exec` 也不管用。要跑什么得先拷到本地，或者显式 `sh x.sh`。所以"在挂载点里跑安装脚本"不成立，安装脚本得用 `bash install.sh` 调。

## 删掉了什么

- `docs/adr/0005-transport-stays-on-iroh.md` —— 它决策的是"留在 iroh / QUIC 上"，而这条路的传输已经不是 iroh 了。仍然成立的那半句（不自己写传输层）已并入决策六。
- `docs/adr/0006-mount-data-path.md` —— 它整份是为"按 hash 取字节、在本地 store 里按范围读"设计的。其中唯一还活着的决策（listing 的单位是**一个目录**）已并入 ADR-0002，其余作废。
- 对应的代码路径（endpoint / store / provider / 索引缓存 / 按范围读 / 链接的 ticket 编码）随实现一起删。

`docs/performance.md` **保留**。它是一次关于 iroh 传输的调查，而那条传输已经删了；留着的理由是两样**跟走哪条路无关**的东西：测量方法论（profiler 会少采、`du` 会被 APFS 的 clonefile 骗、能数计数器就别比耗时），以及一张"哪些路已经堵死"的负面地图——将来真要把 iroh 加回来时，省得重走。

## 重新评估的触发条件

- **对方的平台没有 NFS 客户端**（Windows Home）→ 这条路要么换成 SMB，要么放弃“零安装”这个卖点。这是唯一能推翻决策一的需求。
- **端口 20490 被占**成为实际困扰 → 给它一个配置开关（然后端口就得进链接了）。
- **明文令牌不可接受**（公共网络场景）→ 要么上 NFSv4 加 Kerberos（复杂度立刻上一个量级），要么回到"对方装一个客户端 + 加密隧道"，也就是把 iroh 加回来。
