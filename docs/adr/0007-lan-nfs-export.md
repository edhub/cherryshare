# ADR-0007: 局域网这条主路走只读 NFS 导出

- 状态: Accepted
- 日期: 2026-10-15

## 背景

原本的设计是：创建者用 iroh 把字节发出去，接收侧再挂成本地目录。走到实现阶段发现这个组合在主打场景里不成立。

**主打场景是局域网。** 而局域网里已经有一个成熟的东西在干同一件事：SMB / 文件共享。它零安装、文件系统完整、客户端到处都有。我们写的挂载没有一项比得过它。

**iroh 真正解决的问题只有一个：在没有可达 IP 路径时不用配置、不用账号就能连上。** 局域网里 IP 路径本来就有，所以它的活是空的。而它带来的代价是整套东西：endpoint、blobs store、内容寻址、索引缓存、按范围读、缓存上限与淘汰。这些全都是"用 iroh-blobs 给挂载做传输"的副产品，不是产品要解决的问题。

反过来看，有一个好处我们之前完全没算进去：**对方什么都不用装。** 而拿到这个好处并不需要 iroh——只要让创建者讲一个内核本来就懂的协议。

## 决策

### 一、传输是创建者侧的一个只读 NFS 导出

创建者的服务把 basket 导出成 NFS，对方用系统的 NFS 客户端挂载，不安装 CherryShare。macOS 自带客户端；Linux 可能需要先安装 `nfs-common` / `nfs-utils`。另有 HTTP 浏览和下载入口，见 ADR-0002、ADR-0004。

理由不是"NFS 比 iroh 快"，而是**内核自带的 NFS 客户端把难的部分都做了**：元数据和数据的缓存与淘汰、预读、超时与重试、挂载/卸载、Finder 集成。用 FUSE 做这些要自己写，而 macOS 上 macFUSE 要 kext、FUSE-T 本身就是在**本机跑一个 NFS 服务再挂回环**——既然它都是这么干的，我们直接讲 NFS 就少一层依赖。

服务端用 `nfsserve`（Rust，NFSv3，纯用户态）。它不是玩具：Hugging Face 的 `hf-mount` 就是用它把远端数据集挂成本地只读文件系统，形态和我们完全一样。

实测（macOS 27，本机回环，256 MiB）：冷读 747 MB/s（服务端还是 debug 版）、再读一次 16 GB/s（全在内核 page cache 里，根本没到服务端）、字节与源文件逐字节一致；挂载不需要 root；服务端被杀之后读未缓存的字节报 `Operation timed out`，**不卡死**（默认 `timeo=10,retrans=10` 下约 8 秒）。

### 二、权限模型是能力令牌，不是账号

`basket_id` 是 128 位随机数，它作为**挂载路径的第一段**：`host:/<32 位十六进制>`。不知道 id 就挂不上。

MNT 按路径检查篮子 id，之后客户端使用 file handle。篮子根句柄直接包含完整的 128 位 id，子句柄是篮子 id 与路径的 64 位哈希；处理请求时仍查询篮子的当前定义。因此根句柄仍会明文传递 id，句柄也必须当作访问凭证，不能只保护挂载命令。

当前没有换 id、删除 basket 或吊销链接的操作。停止分享只能移除 cherry 或停服务；新建篮子不会让旧链接失效（ADR-0002）。

**`path_to_id` 必须拒绝 `"/"`。** 这是这个设计成立的前提，不是细节：全局根一旦交出去，客户端 `readdir` 一下就能枚举出所有 basket_id，"密码"就白设了。同理 `lookup` 里的 `".."` 不能返回全局根。

没有任何形式的账号、成员表、登录。**"知道 id"就等于"有权限"**，这和 ADR-0002 里 `basket_id` 的定位一致，只是到这里它才真的被强制执行。

### 三、只读

所有写操作（`setattr` / `write` / `create` / `mkdir` / `remove` / `rename` / `symlink`）一律拒。

属性上不透创建者的身份：uid/gid 报 0，size 和 mtime 报真实值。**权限位照实报**（2026-10-17 改）：原来是把写位一律清掉、报成 `0o444`，好处是 `ls -l` 一眼看出写不了，代价是从共享里拷出来的东西全带着只读位——目录是 `0o555`，`cp -R` 出来那棵树连往里面加文件都不行，`install.sh` 从挂载点上装就把只读位带进了本地安装目录。这些位在对方那边的用途是「看」和「复制」（`cp`、`rsync -a`、`tar`、Finder 拖拽都拿它当目标文件的权限），不是「能不能写」。所以「只读」这件事改由两个更准的地方说：写操作一律回 `NFS3ERR_ROFS`（客户端翻译成 `Read-only file system`，比原来的 `Operation not permitted` 清楚），挂载命令里带 `ro`（客户端那头就把卷标成只读，往 Finder 里拖会出禁止标记）。篮子根是虚拟目录，它那层 mtime 用篮子定义那个配置文件（`baskets.json`）的 mtime，那也是真实的。共享出去的是一份内容，不是那台机器的延伸。

### 四、只共享真文件和真目录

`..` 和符号链接**都不许穿过**，它们是同一个边界的两半。共享目录里出现符号链接时跳过它并警告；如果按名字直接去读，明确的报错，不是静默跟随。

没有这条，共享一个目录就等于共享那个链接指向的任何东西。

### 五、NFS 端口固定

NFS 固定监听 `0.0.0.0:20490`，内部 `cherryshare:` 编码不带端口；挂载命令显式给 `port=20490,mountport=20490`。HTTP 另用 `0.0.0.0:20480`，网页 URL 带这个端口。

任一端口绑定失败都会记错误日志，对应入口不可用，但服务不退出，其他成功启动的入口和本地管理继续运行。`cherry status` 分别显示两者的监听状态。

### 六、iroh 整套删掉，需要通道时再加回来的是一个**端口转发**

现在删掉：endpoint、blobs store、自研 ALPN、内容寻址、索引缓存、按范围读、缓存上限与淘汰。它们全都是为"iroh 传字节给挂载"服务的，那条路没了，它们就没有消费者。

将来若需要跨网，NFS 可以通过现成的 TCP 端口转发连接对端的 20490，不必另造数据协议。当前挂载命令显式给 `port=`、`mountport=` 并关闭 NLM 锁，NFS 这条路只需转发一个端口。若也要网页入口，还需转发 HTTP 端口，并重新考虑链接、挂载命令中的地址及明文传输边界，不能把两条入口都当成只转发一个端口即可。

ADR-0005 里那条仍然成立的内核结论保留在这句话里：**不自己写传输层**，跨网也用现成的。

（2026-10-15 定：**跨网不是场景**。这一段留着只说明“真要加也不是换协议”，不作为路线。）

### 七、分享单位不变，但挂载这件事我们一行代码都不写

basket 仍是分享单位，凭证仍是 `basket_id`。`cherry list` 给网页 URL，不直接打印挂载命令。

网页提供**两个系统的挂载命令**：macOS 用 `mount_nfs -o ro,nolocks,...`，Linux 用 `sudo mount -t nfs -o ro,nolock,...`。快捷复制按钮按浏览器识别的系统选择，展开说明仍可手动选；Linux 需要 root。

**`cherry-mount` 这个独立二进制取消，CLI 里那个 `cherry mount <链接>` 子命令也删了。** 前者原本存在的理由是"要背 macFUSE / FUSE-T 那堆重且平台相关的依赖"，而现在挂载由内核的 NFS 客户端做，我们这边没有平台依赖要背；后者只是把一个现成的命令拼出来再跑一遍，而现在网页统一提供挂载命令，不再由 CLI 维护第二份入口。

## 非目标

- **不做账号 / 成员表 / 登录。** 能力令牌就够了，见决策二。
- **不做 SMB。** 它需要凭证或访客配置，而 id 已经是凭证；实现成本也比 NFSv3 高一个量级。
- **不做 WebDAV。** Finder 里 ⌘K 粘个 http 地址就能挂，而且服务端不支持 `DAV LOCK` 时 Finder 会强制只读——正合我们的只读语义。代价是要写 PROPFIND / OPTIONS / multistatus 那一套 XML，而"挂载"这件事 NFS 那条路已经做了，网页那条路也已经给了 Windows 和 iOS 一个不用装东西的入口。（2026-10-17 定，不做。）
- **不缩短 `basket_id`。** 它要的是不可猜测性，不是唯一性。
- **不自研传输层。** 包括不做 QUIC-over-TCP 那种"看起来像自研"的绕路。
- **不做服务端缓存。** 创建者直接把磁盘上的文件读给对方，中间没有副本要管；对方那边的缓存由内核管。
- **不做跨网。** 那是将来加一个端口转发的事，不是现在。

## 后果

正面：

- **对方不用安装 CherryShare。** 可以用浏览器看和下载；挂载需要系统的 NFS 客户端，Linux 可能需另装客户端包。macOS Finder 中能浏览、预览和复制。
- 没有 store、内容寻址或内容缓存淘汰。文件服务使用 NFS 和 HTTP，不自研底层传输协议。
- 没有 store 的生命周期问题（上限、淘汰、保护、以及"分享的文件被复制进 store"）。创建者读的就是用户自己的文件。
- NFS 挂载失败、读取超时、写入被拒都有错误。接收者仍可能看到缓存；网页 zip 还可能跳过或截短读取失败的文件，完整限制见 `docs/errors.md`。

负面：

- **只支持可信局域网场景。** 没有跨网发现、穿透或隧道；可达的其他网段也可能连上，但不是跨网能力或安全隔离。
- **令牌不可猜测，但传输不加密。** NFSv3 和当前 HTTP 都会明文传 id，还可能留在浏览器历史、挂载表和 shell history 里。不用于不可信网络。
- **创建者开放了两个网络监听**，均绑定 `0.0.0.0`。HTTP 的现有边界见 ADR-0004，不能用 local socket 的权限保证来描述这两个端口。
- **Windows 和 iOS 的使用入口是网页**，提供浏览和下载，不承诺这些系统都有可用的 NFS 客户端。
- 目录列表可见延迟取决于客户端缓存。生成的命令给 `actimeo=5`，macOS 实测等待缓存过期后能看到变化，不作为所有客户端的严格上限。
- **macOS 实测重启后无需重挂**：fileid 是路径的哈希，句柄就用它；篮子根另一种形态，把 128 位篮子 id 直接放进去——因为它是新进程里唯一必须能被“冷”解析的。所以 `ls` 挂载根、`ls` 子目录、`df` 从重启后的第一秒起就是好的；碰到客户端缓存里那些**子句柄**时会报一次 `Stale NFS file handle`，但客户端会自己按名字重新 lookup，**实测两三秒后就全好了**（整棵树 `diff -r` 无差异，不用重挂）。
- **但已经打开、正在读取的文件可能仍会失败**：那个句柄被进程握着，重启后报错，只能关掉重开（跑到一半的 `cp` / `rsync` 得重来）。这是这套句柄方案的天花板：非根句柄不可逆（哈希），所以新进程没法替一条冷句柄反推出路径。要再进一步就得把句柄里塞路径（64 字节放不下深路径），或者启动时走一遍整棵树——两条都不值。
- **此前的 macOS 挂载实测中，直接执行脚本或二进制曾报权限错误**，当时加 `-o exec` 也未解决。这不是已验证的跨平台 NFS 规则。发布包统一要求 `bash install.sh`；脚本先把自己和二进制复制到本地，再重启服务，避免执行期间挂载失效。

## 删掉了什么

- `docs/adr/0005-transport-stays-on-iroh.md` —— 它决策的是"留在 iroh / QUIC 上"，而这条路的传输已经不是 iroh 了。仍然成立的那半句（不自己写传输层）已并入决策六。
- `docs/adr/0006-mount-data-path.md` —— 它整份是为"按 hash 取字节、在本地 store 里按范围读"设计的。其中唯一还活着的决策（listing 的单位是**一个目录**）已并入 ADR-0002，其余作废。
- 对应的代码路径（endpoint / store / provider / 索引缓存 / 按范围读 / 链接的 ticket 编码）随实现一起删。

`docs/performance.md` **保留**。iroh 部分是历史调查，不描述当前 NFS / HTTP 的性能；其中的测量方法和已试过的方案仍可参考。文件另有当前网页 zip 压缩的测量记录，需与历史部分分开读。

## 重新评估的触发条件

- **对方的平台没有可用的 NFS 客户端** → 这条原来是唯一能推翻决策一的需求。2026-10-15 补：网页那条路给了第三个答案——不用换协议，也不用放弃“零安装”，代价是那条路只能看和拿，不能挂。
- **端口 20490 被占**成为实际困扰 → 评估 NFS 端口配置，同时调整挂载命令和必要的链接信息。
- **明文令牌不可接受**（公共网络场景）→ 要么上 NFSv4 加 Kerberos（复杂度立刻上一个量级），要么回到"对方装一个客户端 + 加密隧道"，也就是把 iroh 加回来。
