# 失败清单

见 ADR-0001 的前提：这是两个人之间、有明确沟通的分享场景，可靠性主要由人兜底。所以这里不追求消除失败，只追求**每个失败都有明确、可读、可恢复的终态**。

本文件随实现持续更新，不属于 ADR。

## 查看者侧

| 场景 | 终态 |
| --- | --- |
| 创建者不在线、地址不对、不在同一个网里 | 挂载时明确失败（系统的挂载命令报错，macOS 是 `mount_nfs`），**不会挂上一个空目录** |
| `basket_id` 不存在或已吊销 | 挂载时 `No such file or directory`。**不区分"不存在"和"无权限"**，本来是一回事 |
| 挂上之后创建者退出 / 断网（服务不在了） | 读报 `Operation timed out`，**绝不挂起**——调用方（`ls`、Finder、`df`）没有超时，挂起就是把别人的进程拖死。实测 `soft` 挂载下约 8 秒报错 |
| 挂上之后创建者那边的服务**重起了**（崩溃自动重起、开机、装了新版） | **不用重挂。** 挂载根、列目录、`df` 从第一秒起就是好的（篮子根的句柄里放的就是篮子 id，新进程认得）。碰上客户端缓存里的子句柄时会报一次 `Stale NFS file handle`，但它会自己按名字重新 lookup，实测两三秒后恢复 |
| 服务重起时你正**打开着**某个文件（跑到一半的 `cp` / `rsync`） | 那个句柄跑不掉了，报错就是报错，关掉重开（拷贝得重来） |
| 创建者移动或删除了某颗 cherry 的文件 | 那个路径读报 `No such file or directory`；下次列目录它就不在列表里了（listing 是活的）。创建者那边的服务发现之后会把这条引用摘掉，**别的 cherry 不受影响** |
| 尝试写入（新建、删除、改名、改属性） | `Read-only file system` 或 `Permission denied` |
| 共享目录里有符号链接 | 它不出现在列表里（创建者侧记一条警告）；按名字硬读报明确的 `No such file or directory`，**不是静默跟随** |
| 创建者增删了一颗 cherry | 最多 `actimeo` 秒（现在 5 秒）后可见。这是**有界的**陈旧，不是静默失效 |
| 看到的 owner 是 `root`、权限是只读 | 故意的：不透创建者的身份，也不假装可写 |

## 创建者侧

| 场景 | 终态 |
| --- | --- |
| 添加路径时读不到（含系统权限未授予） | 当场拒绝，不进 basket |
| 分享中文件被移走或被删（含外置盘拔了） | 那颗 cherry 从篮子里摘掉，只留一条日志。**当场没有提示**：这件事发生在没人看着的时候，日志在 `~/Library/Logs/cherryd.log`，里面带着把同一路径加回来的命令 |
| 分享中权限被撤销、IO 出错 | 可能是一时的，**不摘**，留着；那条路径读写时报错 |
| cherry 的名字与已有的冲突 | 拒绝添加，要求改名 |
| 列表里有条目被跳过（符号链接、设备、名字不是 UTF-8） | 记一条警告，该条目不出现在列表里 |
| NFS 端口（20490）被占 | 启动时**明确失败并说明局域网挂载这条路不可用**；本地其余功能照常，服务不退出 |

原则见 ADR-0001 的前提。两条需要额外说明的：

**没有中间状态可丢。** 字节直接从创建者的磁盘流到对方的内核，我们这边不落副本。所以"下载完了但导出失败"这类场景不存在了——失败就是失败，重试就是重新读。

**文件级的断点续传不由我们提供。** NFS 只保证传输层的可靠，一次 `cp` 中途断了就得重来。要续传就用 `rsync` 这类工具（对方那边的标准操作）。跨网那条路（ADR-0007 决策六）加上之后，这一点会更重要，届时得重新考虑。
