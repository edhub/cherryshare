# 失败清单

见 ADR-0001 的前提：这是两个人之间、有明确沟通的分享场景，可靠性主要由人兜底。所以这里不追求消除失败，只追求**每个失败都有明确、可读、可恢复的终态**。

本文件随实现持续更新，不属于 ADR。

## 查看者侧

| 场景 | 终态 |
| --- | --- |
| 连不上创建者 | "创建者当前不在线" |
| `tap_id` 不存在或已吊销 | "这个链接已失效"（不区分"不存在"和"无权限"，本来是一回事） |
| 某个条目创建者已无法提供（被改 / 被删） | 条目标为不可用，点击提示"创建者已修改或移除了它，刷新一下" |
| 传输中断（网络断开、对端退出） | 自动续传；彻底失败则"已保留进度，可重试" |
| 本地空间不足 | 开始传输前就明确报错 |
| 导出到目标目录失败（权限、同名冲突） | 提示；**不得丢弃 store 里已下完的副本** |

## 创建者侧

| 场景 | 终态 |
| --- | --- |
| 添加路径时读不到 | 当场拒绝，不进 tap |
| 分享中文件被移走、权限变了、外置盘拔了 | 下次索引时标为不可用 |
| 条目名与已有条目冲突 | 拒绝添加，要求改名 |

## 三条原则

1. **不静默失败。** 宁可报错，也不要展示一份陈旧的状态让人以为一切正常。
2. **可恢复优先于可理解。** 大文件中途失败时，光有提示不够，必须能续传。
3. **已下载的字节不因后续步骤失败而丢弃。** 下载完成但导出失败时，副本留在 store 里等重试。这与"store 只是传输工作区"不矛盾：工作区的生命周期覆盖到"用户拿到为止"，而不是"传输完成"。
